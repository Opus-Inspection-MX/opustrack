### Approaches

1. **Hand-written RENAME migration (plan-locked, validated)** — `ALTER TABLE "Cliente" RENAME TO "Client"`, RENAME columns/indexes/constraints, `UPDATE Permission` (`name`/`resource`/`routePath`) + `UPDATE Role` (`defaultPath`) mirroring `20260508032555` sections 1-6. Follow the WorkOrder precedent, NOT the Vic→Cliente DROP+CREATE.
   - Pros: zero data loss; junction rows preserved; permission UPDATEs keep `RolePermission` ids stable (no lockout from dangling grants); reviewable SQL.
   - Cons: must enumerate every index/constraint name by hand; `@@unique([userId, clienteId])` compound name changes (`userId_clienteId` → `userId_clientId`) and every call-site must match.
   - Effort: Medium
2. **Regenerate / DROP+CREATE migration (rejected)** — what `20260609000000` did (`DROP TABLE VehicleInspectionCenter`, `DROP COLUMN vicId`).
   - Pros: none for a live rename.
   - Cons: destroys Cliente/Incident/Line data; orphans assignments; unacceptable.
   - Effort: Low (and wrong)
3. **Audit: explicit actor stamping via `requirePermission` (plan-locked, validated)** — each mutating action passes `user.id` into `logAudit(tx, { actorId: user.id, … })`; no request-scoped global.
   - Pros: matches existing auth helpers (actor already in hand); Edge-safe; testable (pass any id); no ALS context-loss risk in Server Actions/transactions.
   - Cons: every writer call-site must remember to pass the actor (lint/review discipline).
   - Effort: Medium
4. **Audit: AsyncLocalStorage actor propagation (rejected — state why)** — store actor in ALS at action entry, `logAudit` reads it implicitly.
   - Pros: shorter call signatures.
   - Cons: ALS does not reliably propagate through Next.js Server Action + `prisma.$transaction` boundaries; silent `null` actors; invisible coupling; harder unit tests. Explicit is correct here.
   - Effort: Medium (plus debugging)
5. **Observability: stdlib-only edge-safe logger in `src/lib/observability/` (plan-locked, validated)** — `logger.{info,warn,error}` with level gating + denylist redaction (`password`, `token`, `secret`, `authorization`, `cookie`, `sessionToken`, …), JSON to stdout in prod, pretty in dev; `instrumentation.ts onRequestError` forwards; `withPermission` splits authz-denials (403, no log) from handler faults (500, logged).
   - Pros: zero new dependencies (no `deps:freeze` needed); Edge-compatible (no node:fs); satisfies plan without supply-chain churn.
   - Cons: less structure than pino; must keep redaction list in sync manually.
   - Effort: Medium

### Recommendation

The locked plan is sound and fully validated against the codebase: hand-written RENAME migration per the `20260508032555` precedent; `sessionVersion` bump required ONLY in Phase 2 (role/permission renames invalidate JWT claims — Phase 1 table/column renames do not change the permission-name strings the JWT carries… spec must confirm whether Phase 1 renames permission rows or defers them; if permission `name` values change, the bump moves with them); audit via explicit stamping (ALS rejected); stdlib logger (no new dep). Execute in the suggested 4-PR split (1. Cliente→Client atomic, 2. CLIENT→REPORTER, 3. audit, 4. observability) because PR 1 alone touches ~130 files and the 400-line review budget forces slices regardless. Next: `sdd-propose`, then `sdd-spec` (new spec 11, RF-550–599) and `sdd-design` (exact RENAME statement list + column matrix + logger API).

### Risks

- **Lockout**: permission/role `UPDATE`s + JWT claim drift → force re-login via `sessionVersion` increment in the same migration/deploy (Phase 2). Propose must include a rollback re-rename.
- **Data loss**: any DROP/CREATE or missed FK constraint rename breaks referential integrity — RENAME-only SQL + ephemeral-DB e2e gate (`npm run test:e2e`, never the real DB; `db-guard` refuses non-local hosts).
- **Private seed drift**: real `initial_load/seed.ts` is gitignored — the tracked `seed.example.ts` rename must be mirrored by whoever holds the real file, or local prod-like environments break silently.
- **Coverage gate**: vitest thresholds 75% lines/functions/branches/statements — mass renames must not delete or orphan tests; `vi.mock` path renames (7 files) fail loudly if missed, which is good.
- **Knip gate**: new `observability/` module + `instrumentation.ts` must be wired into an entry path or `npm run check` (biome + tsc + knip) fails CI.
- **Spec/prose drift**: `spec/` vs `CLAUDE.md` VIC/WorkOrder remnants already exist; the rename must not widen it — code identifiers English, prose Spanish, filename `02-clientes-jerarquia.md` kept.
- **`clientIds` collision**: `actions/clientes.ts:23` uses `clientIds` for CLIENT-user ids; after Cliente→Client it reads as Client-entity ids. Spec must mandate `reporterIds` (or equivalent) before apply.
